# 저자 톤 (base)

저자의 글이 기계적·구어체·즉흥적으로 읽히지 않게 유지하는 규칙.
`readability.md CJ2`(합쇼체 통일)를 전제로 하며, 그 위에 문장 구조·용어 선택·메타 구성의 일관성을 더한다.

> **연계**: 톤 위반은 대부분 `ai-tells.md`의 카테고리와 1:1 매핑된다. 예: T1 ↔ J-3 (em dash), T8 ↔ A-7·D-5 등.

**적용 범위**: 한국어 마크다운 산출물. 여기에 더해 **용어 선택 규칙(T5·T6·T17)은 어시스턴트 대화 응답에도 적용된다.** 독자가 쓰지 않는 말을 고르는 실패는 매체와 무관하게 같은 형태로 나타난다. 문장 구조·메타 구성 규칙(T1~T4·T7~T16)은 문서 전용이다.

> 분량은 반대다. `length.md` 가 대화 응답 분량을 범위 밖으로 두고 `~/.claude/CLAUDE.md` 로 넘긴 것과 이 선언은 어긋나지 않는다. 용어는 매체가 달라도 판정이 같고, 분량은 매체마다 달라진다.

## T1. em dash(—) 금지

한국어 본문에서 em dash(`—`) 사용을 금지한다.
**콜론(`:`)**, **쉼표(`,`)**, **괄호(`()`)**, **줄바꿈** 중 문맥에 맞는 기호로 대체한다.

> **근거**: em dash는 영어권 편집 관행에서 주로 쓰이며, 한국어 문어에서는 읽는 리듬이 끊긴다.
> AI가 생성한 한국어 글에서 과도하게 등장하여 "AI 티"의 대표 신호가 됨.

Bad:
```markdown
Forward Auth는 데이터 경로와 인가 경로의 분리 — 이것이 핵심이다.
```

Good:
```markdown
Forward Auth의 핵심은 데이터 경로와 인가 경로의 분리다.
Forward Auth의 핵심은 데이터 경로와 인가 경로의 분리(decoupling)다.
```

`ai-tells.md J-3` 와 동일 규칙.

## T2. 어순 전환·두 문장 도치 금지

구어체 목적어 종결(`~다는 걸요`, `~사실을요`)을 금지한다.
또한 "완결 선언 후 목적절만으로 된 뒷 문장"을 덧붙이는 두 문장 도치 구조도 금지한다.
목적어가 필요하면 한 문장 안에서 완결한다.

Bad:
```markdown
나중에야 알게 됐습니다. 이 방식이 정형 패턴이라는 걸요.
나중에야 알게 됐습니다. 이 방식이 정형 패턴이라는 것을.
```

Good:
```markdown
이 방식이 정형 패턴이라는 사실을 나중에야 알게 됐습니다.
```

## T3. 서술어 생략된 체언 종결 금지

"A는 종전과 동일, B는 새 필드." 처럼 서술어가 생략된 명사구 종결 문장을 금지한다.
대비·나열이 필요해도 각 절에 서술어를 붙여 완결한다.

Bad:
```markdown
외부에서 보면 기존 API는 종전과 동일, 신규 API는 새 필드.
```

Good:
```markdown
외부에서 보면 기존 API는 종전 응답을 그대로 유지하고,
신규 API만 새 필드를 노출합니다.
```

**예외 (항목 나열 블록, 개조식)**: 목록·표처럼 한 줄에 한 항목을 담는 블록에서는 체언 종결을 허용한다. 인덱스로 훑어읽는 형태라 서술 종결로 늘리면 줄당 정보량이 떨어져 블록의 목적이 깨진다.

이 표기를 **개조식**(箇條式)이라 부른다. 서술식과 대비되는 이름이므로 "이 블록은 개조식으로" 같은 지시가 그대로 통한다.

두 조건을 **모두** 만족해야 예외다.

| 조건 | 내용 |
|------|------|
| 1. 블록 내 일관성 | 그 블록의 모든 항목이 같은 종결이다. 한 블록에서 체언 종결과 서술 종결이 섞이면 위반이다 |
| 2. 항목당 한 사실 | 한 항목에 사실 하나만 담는다. `~하고`·`~라서` 같은 접속으로 두 사실을 이으면 문장이므로 서술어를 붙여 완결한다 |

Bad (한 블록에서 종결이 섞임):
```markdown
- 요청 타임아웃 상향
- 재시도 횟수를 3회로 늘렸습니다
- 실패 응답 캐시 제거
```

Good (체언 종결로 통일):
```markdown
- 요청 타임아웃 상향
- 재시도 횟수 3회로 상향
- 실패 응답 캐시 제거
```

Good (서술 종결로 통일):
```markdown
- 요청 타임아웃을 상향했습니다.
- 재시도 횟수를 3회로 늘렸습니다.
- 실패 응답 캐시를 제거했습니다.
```

Bad (한 항목에 두 사실을 접속으로 이음):
```markdown
- 재시도 횟수 3회로 상향하고 실패 응답 캐시를 제거해 오탐 감소
```

**문단에는 예외가 없다.** 목록 밖의 산문에서 서술어를 생략하면 이 예외와 무관하게 위반이다. 같은 문서에서 상단 목록은 체언 종결, 하단 본문은 서술 종결로 가는 구성이 정상이며, 블록 단위로 판정하므로 이 구성이 그대로 통과한다.

> **왜 문서 유형 단위가 아니라 블록 단위인가**: 유형 단위로 예외를 주면 그 유형의 산문 문단에서도 체언 종결이 열린다. T3 가 원래 잡으려던 문제가 그 자리에서 다시 나온다. 반대로 예외 없이 두면 목록이 많은 유형 전반에서 정상 표기가 매번 위반으로 잡힌다. 판정 단위를 블록으로 내리면 양쪽이 해결된다.

## T4. 도입부 메타 설명 중복 금지

도입부에 "이 글이 무엇을 다루는가"를 설명하는 메타 문단을 **1회로 제한**한다.
TL;DR이 이미 메타 요약 역할을 하므로, 본문 진입 전 별도 "이 글은 ~에 중심을 둡니다" 같은 문단을 추가하지 않는다.

> **근거**: 메타 설명이 연속되면 본론 진입이 지연되어 독자가 이탈한다.
> TL;DR + 도입부 한 문단이면 충분하다.

## T5. 즉석 명명 회피, 교과서 용어 우선

정식 용어(업계 표준, 교과서 표기)가 존재하는 개념을 "편의상 X라고 부르겠습니다" 식으로 즉석 명명하지 않는다.
먼저 정식 용어를 탐색하고, 기존 용어가 있으면 그것을 사용한다.
즉석 명명이 불가피한 경우(팀 내 전용 약어 등)에만 명시적 도입을 허용한다.

Bad:
```markdown
이렇게 두 버전이 공존해도 깨지지 않는 상태를 편의상 N-1 호환성이라고 부르겠습니다.
```

Good:
```markdown
이렇게 여러 버전이 공존하는 중간 상태를 **version skew**라고 부릅니다.
이 상태에서 깨지지 않는 성질이 **하위 호환성(backward compatibility)**입니다.
```

## T6. 영어 전문 용어 첫 등장 시 괄호 풀이

`readability.md CJ3`(외래어 표기) 원칙을 톤 차원에서 강화한다.
`write-both`, `version skew`, `backward compatibility`, `schema-only` 등 영어 전문 용어는
**첫 등장 시 괄호로 한국어 풀이 또는 한국어 표기 + 괄호 원어 병기**한다.
이후 반복은 원어만 써도 무방하다.

Bad:
```markdown
Migrate 단계에서 쓰기는 write-both 기간을 둡니다.
```

Good:
```markdown
Migrate 단계에서 쓰기는 레거시·신규 양쪽에 하는(write-both) 기간을 둡니다.
```

## T7. 기계적 수치 강조체 금지

숫자를 형용사처럼 붙여 강조하는 표현을 금지한다.
`변화 0`, `비용 0`, `위험 0`, `의존 0`, `차이 0` 같은 패턴은 영어식 간결체("zero impact", "no change")를 반사 번역한 결과로,
한국어 기술 문서 관용에 맞지 않아 공신력을 떨어뜨린다.

Bad:
```markdown
외부 계약 변화 0이라 독립 MINOR bump는 불필요합니다.
이 경로는 런타임 의존 0, 빌드 비용 0입니다.
```

Good:
```markdown
외부 계약에 변화가 없어 독립 MINOR bump는 불필요합니다.
이 경로는 런타임 의존이 없고, 빌드 비용도 들지 않습니다.
```

## T8. 구어체·감정체 동사 금지

두 범주의 동사를 기술 문서 본문에서 사용하지 않는다.

1. **감정·파괴 계열**: `터지다`, `박살나다`, `날아가다`, `죽다`
   → 중립 동사(`발생하다`, `손상되다`, `유실되다`, `중단되다`, `실패하다`)로 대체
2. **물리 조작 계열**: `떼어내다`, `끼우다`, `박아넣다`, `쑤셔넣다`, `꽂다`, `묶다`(제한·구속 의미로 쓸 때), `빼다`(제거 의미), `쪼개다`(분할 의미), `때려박다`, `내리다`(등급·수준 하향 의미)
   → 추상적 중립 동사(`분리하다`, `삽입하다`, `포함하다`, `개입하다`, `제한하다`, `제외하다`, `분할하다`, `낮추다`)로 대체

합쇼체 포멀 톤과 충돌하고, 사실 서술을 감정·행위 서술로 바꿔 공신력을 떨어뜨린다.

### 어조가 튀지 않는 물리 동사

위 두 범주는 어조가 튀어서 눈에 걸린다. 그런데 같은 물리 어근이면서 어조는 평범한 동사가 있고, 이쪽이 실제로는 더 자주 남는다. 손으로 하는 동작을 그대로 가져와 추상 관계를 서술하는 것은 같으므로 대상은 같다.

| 동사 | 추상 대상에 쓸 때 | 대체 |
|------|------------------|------|
| `잇다`·`이어 붙이다` | 서비스·로그·구간을 연결한다는 뜻으로 | `연결하다`, `상관시키다` |
| `붙이다` | 항목·비교·근거를 추가한다는 뜻으로 | `추가하다`, `보완하다` |
| `가르다`·`갈리다` | 판단·경우가 나뉜다는 뜻으로 | `나누다`, `분할하다`, `경우에 따라 달라지다` |
| `벗기다` | 접두사·계층·포맷을 제거한다는 뜻으로 | `제거하다`, `분리하다` |
| `뽑다`·`뽑아내다` | 필드·값·데이터를 얻는다는 뜻으로 | `추출하다` |
| `빠지다` | 문제·항목이 없어진다는 뜻으로 | `없어지다`, `해소되다`, `제외되다` |
| `넘기다` | 대상·작업을 다른 주체에게 준다는 뜻으로 | `전달하다`, `맡기다`, `위임하다` |
| `덮다` | 범위·구간을 포함한다는 뜻으로 | `커버하다`, `포함하다`, `아우르다` |
| `가리키다`·`지목하다` | 값·대상을 지시한다는 뜻으로 | `참조하다`, `식별하다`, `특정하다` |
| `닿다` | 단계·범위에 이른다는 뜻으로 | `이르다`, `적용하다`, `도달하다` |

`가르다`·`뽑다` 는 대체어가 1:1 로 잡혀 `forbidden-words.json` 에 등록한다. 나머지는 일상 용례가 흔해 정규식으로 판정하지 않고, 밀도를 `physical_verb_count` 로 보고한다.

**등록 패턴은 어절 시작에서만 매칭한다.** `헷갈리다`·`엇갈리다` 는 앞에 다른 형태소가 붙어 뜻이 달라진 말이라 대상이 아니다. 분별이 어렵다는 뜻이고 `나누다`·`분할하다` 로 바꾸면 문장이 성립하지 않는다.

물리 실체를 다루는 문장에서는 그대로 쓴다. `케이블을 뽑는다`, `스티커를 붙인다` 는 대상이 물리라 조건에 걸리지 않는다.

### 판정 기준 (목록에 없는 동사)

위 목록은 예시이지 전체가 아니다. 등록 패턴 대조만으로는 같은 계열의 다른 동사를 놓친다. 목록에 없는 동사는 아래 세 조건으로 판정한다.

| 조건 | 설명 |
|------|------|
| 대상이 추상인가 | 도구·로직·규칙·모듈처럼 물리 실체가 없는 대상에 붙었는가 |
| 동사가 물리 조작·파괴인가 | 손으로 하는 동작이나 파괴를 뜻하는 어근인가 |
| 어휘 쌍이 깨지는가 | 문서가 쓰는 행위 어휘 쌍(`나누다`↔`합치다`)을 한쪽만 구어로 바꾸는가 |

세 조건을 모두 만족하면 순화한다.

**예외**: 도메인 어휘와 정합하는 은유(`계층을 쌓는다`: `쌓다`↔`층`), 확립된 관용구(`흔들리다`), IT 표준 한국어(`연결이 끊기다`)는 유지한다.

`가르다` 는 예외에서 제외했다. 관용구로 통하지만 `나누다`·`분할하다` 라는 대체어가 그대로 있어 예외를 둘 이유가 없고, 예외로 두는 동안 규칙이 오히려 통과시켰다.

### 정규식이 담는 범위

hook 등록 패턴은 **어간 + 어미 묶음**으로 쓴다. 활용형을 항목마다 열거하면 계열마다 다시 빠뜨린다. `가르다` 는 관형형이, `박다` 는 `박고` 가 그렇게 통과했고 두 건이 따로 제기됐다.

어미 묶음은 `forbidden-words.json` 의 `_endingClass` 가 한 번 선언하고 패턴에서 `%E%` 로 참조한다. 동사를 더할 때 적는 것은 어간이다.

모음이 어간에 녹아드는 활용형(`박혀`·`갈립니다`)은 어간 결합으로 나오지 않으므로 어간 자리에 함께 적는다. 자음 어미는 묶음이 덮는다.

**정규식은 이 부류를 닫지 못한다.** 한국어 활용은 어간이 변형되고, 같은 계열의 다른 동사는 등록돼 있지 않다. 등록 패턴은 흔한 형태를 잡을 뿐이고, 부류 판정은 아래 [판정 기준](#판정-기준-목록에-없는-동사) 세 조건이 한다. **검출 0건을 통과로 읽지 않는다.**

Bad (감정·파괴):
```markdown
문제가 터졌을 때 돌아갈 수 없음.
배포가 실패하면 데이터가 날아갑니다.
장애 나면 서비스가 죽습니다.
```

Good:
```markdown
문제가 발생했을 때 돌아갈 수 없음.
배포가 실패하면 데이터가 유실됩니다.
장애 시 서비스가 중단됩니다.
```

Bad (물리 조작):
```markdown
인가 서비스를 데이터 경로에서 떼어내는 방법을 찾았습니다.
인가 서비스가 데이터 경로에 끼어 대역폭을 묶는 문제가 있습니다.
경로에서 불필요한 인가 경유를 빼고 판정만 남깁니다.
```

Good:
```markdown
인가 서비스를 데이터 경로에서 분리하는 방법을 찾았습니다.
인가 서비스가 데이터 경로에 개입해 대역폭을 제한하는 문제가 있습니다.
경로에서 불필요한 인가 경유를 제외하고 판정만 남깁니다.
```

## T9. 임의 신조어 합성 금지

기술 약어·태그(`chore`, `feat`, `fix`, `WIP`, `PR`, `MR` 등) 뒤에
문학적·구어적 동사 어근을 붙여 **즉석 합성어**를 만들지 않는다.

> **근거**: 기술 약어는 관습적으로 고정된 범주다.
> `chore 편승`, `feat 끼워넣기`, `WIP 얹기` 같은 합성은 저자가 만든 일회성 표현으로,
> 독자에게 친숙하지 않고 번역·검색 모두에서 통용되지 않는다.

Bad:
```markdown
SemVer 관점: chore 편승
이번 작업은 다음 릴리즈에 feat 끼워넣기 예정입니다.
```

Good:
```markdown
SemVer 관점: 독립 bump 불필요
이번 작업은 다음 릴리즈에 chore 커밋으로 함께 포함시킬 예정입니다.
```

## T10. 키보드 외 수학·논리 기호 남용 금지

수학·논리 기호(`⊆`, `⊂`, `⊇`, `⊃`, `∈`, `∉`, `∀`, `∃`, `∅`, `≤`, `≥`, `≠`, `≈`, `⇒`, `⇔`, `∴`, `∵`)를 기술 문서 본문에서 사용하지 않는다.
키보드로 직접 입력할 수 없어 저자가 매번 복사·유니코드 입력을 해야 하고,
독자도 동일한 이유로 검색·인용이 어렵다.

- 자연어로 풀어 쓴다: `부분집합`, `이상·이하`, `같지 않다`, `따라서`, `왜냐하면`
- 코드·수식 맥락에서는 ASCII로 대체한다: `!=`, `<=`, `>=`, `->`, `=>`

Bad:
```markdown
"파티션 키 ⊆ 유일성 키" 제약 때문에 단일 PK를 포기했습니다.
@A ≠ @B 라는 점에 주의해야 합니다.
x ∈ S 인 모든 원소에 대해 검증합니다.
```

Good:
```markdown
"파티션 키는 유일성 키의 부분집합"이라는 제약 때문에 단일 PK를 포기했습니다.
@A와 @B는 다르다는 점(@A != @B)에 주의해야 합니다.
집합 S에 속하는 모든 원소에 대해 검증합니다.
```

`ai-tells.md J-4` 와 동일 규칙.

## T11. 권위 용어 남발 금지

"패턴", "표준", "베스트 프랙티스", "모범 사례" 같은 권위 용어는
**공신력 있는 참조가 있을 때만** 사용한다.
통용 용어·구현체별로 이름이 분화된 개념·저자 개인 명명에는
"방식", "접근법", "구조" 같은 중립 명사를 쓴다.

**허용되는 공신력 참조 예시**:
- GoF 디자인 패턴: Singleton, Factory, Observer 등
- Enterprise Integration Patterns, Martin Fowler 저서 수록 패턴: Circuit Breaker, Strangler Fig, BFF, Saga, CQRS 등
- 공식 표준·RFC: HTTP, OAuth 2.0, OIDC 등

Bad:
```markdown
Forward Auth 패턴: GW가 판정을 위임하는 패턴입니다.
(Forward Auth는 구현체별로 이름이 분화된 통용 용어)

REST 패턴을 따른 것이 베스트 프랙티스입니다.
(개인 판단에 "베스트 프랙티스" 붙임)
```

Good:
```markdown
Forward Auth는 GW가 판정을 위임하는 방식입니다.

여기서는 REST 스타일을 따르는 것이 적합하다고 판단했습니다.
```

## T12. 분석 틀 라벨 헤딩 노출 금지

PAAR·STAR·ABCDE 같은 분석 프레임워크의 단계 표시(`P.`, `A1.`, `R.`),
순차 단계 번호(`Step 1:`, `Phase 2:`), 알파벳 분류 표지(`A.`, `B.`, `C.`)를
헤딩에 노출하지 않는다. 구조는 콘텐츠 흐름과 헤딩 텍스트에서 자연스럽게 드러나야 한다.

Bad:
```markdown
## P. 문제
## A1. 어디서 stale이 발생하는가
## A2. 근본 원인
## A3. 재검증 흐름
## A4. 수정
## R. 결과와 재실측
```

Good:
```markdown
## 문제
## 어디서 stale이 발생하는가
## 근본 원인
## 재검증 흐름
## 수정
## 결과와 재실측
```

자동 판별: 헤딩 텍스트가 `^[A-Z][0-9]?\.\s` 또는 `^Step \d+:` 또는 `^Phase \d+:` 패턴으로 시작하는가.

## T13. 사례·관찰 서술은 1인칭 회상으로 통일

저자가 직접 관여한 작업·관찰·판단을 묘사할 때는 1인칭 회상 톤(`확인했습니다`, `예상했습니다`, `추적했습니다`, `재현했습니다`)을 쓴다.
3인칭 기계식 묘사나 익명 수동태(`재현되었습니다`, `검출되지 않았습니다`)는 회피한다.

> **근거**: 글을 쓰는 시점에 저자는 이미 1인칭이다.
> 사례 회상을 시스템 보고서처럼 3인칭 기계식으로 묘사하면 저자가 사라진 보고서 톤이 되어 회고 서술의 저자성·신뢰도가 떨어진다.

**예외 (3인칭 현재형 허용)**:
- 시스템·표준의 일반 동작 정의: `브라우저는 같은 URL 재방문 시 ... 안 합니다`, `Swift는 PUT마다 ETag를 발급합니다`
- 인용·참조의 객관 진술

Bad:
```markdown
4번이 적용되어 브라우저가 자체 추정으로 진입했습니다.
테스트 환경에서 e2e로 재현되었습니다.
ETag 변경은 검출되지 않았습니다.
```

Good:
```markdown
1~3번이 빠진 상태라 4번 heuristic이 적용된 것이라고 예상하고 추적했습니다.
테스트 환경에서 e2e로 재현했습니다.
ETag 변경을 알아챌 기회 자체가 없었습니다.
```

## T14. 방어적·변명조 프레이밍 금지

오지 않은 반론을 가정해 변명하듯 서술하지 않는다.
"말로만 ~한 게 아니라", "단순히 ~가 아니라" 같은 도입은 근거를 대기도 전에 방어 태세를 취해, 저자가 확신이 없어 보이게 만든다.
사실은 있는 그대로 진술하고, 근거는 예시·코드·데이터로 보인다.

또한 이미 명확한 내용을 재강조하는 과장으로 담백함을 잃지 않는다.
`ai-tells.md D-4~D-7`(과장 형용사)이 어휘 단위 하한선이라면, 이 규칙은 문장·구성 단위에서 부풀리지 않기를 요구한다.

> **근거**: 명확한 내용은 담백하게 전달할 때 힘이 산다.
> 변명조·과장조는 저자가 확신이 없어 보이게 만들어 신뢰를 깎고, 개발 문서에서 특히 공신력을 떨어뜨린다.

Bad:
```markdown
말로만 격리했다고 되는 게 아니라 코드에 이음새가 있어야 합니다.
이건 단순한 리팩터링이 아니라 아키텍처 개선입니다.
```

Good:
```markdown
격리는 코드의 이음새로 드러납니다.
이 변경은 어댑터 교체 지점을 한 곳으로 모읍니다.
```

`ai-tells.md D-4~D-7`(과장 형용사)의 문장·구성 단위 카운터파트.

## T15. 메타 어필 직접 노출 금지

글의 홍보·평가 목적(면접·채용·포트폴리오·이력서 대비 등)을 본문 서술에 직접 명시하지 않는다.
독자를 어떤 자리에서 만나려는지는 매체를 고르고 주제를 정하는 단계의 전략일 뿐, 본문 문장이 될 수 없다.
어필은 판단·트레이드오프·근거의 질로 드러난다. "이 경험이 나를 어떻게 보이게 하는가"를 문장으로 쓰면, 내용이 아니라 의도가 앞서 신뢰를 깎는다.

> **근거**: 독자는 저자가 무엇을 판단했는지를 보고 역량을 읽는다.
> "면접 빈출 주제", "시니어로 가는 발판", "포트폴리오로" 같은 메타 서술은 그 판단을 대신 평가해 달라는 요청이라, 오히려 근거의 자리를 밀어낸다.

대상 어휘(서술문에 등장 시 위반): `면접`, `채용`, `시니어`/`주니어`, `포트폴리오`, `이력서`, `역량을 보여`, `나를 증명`.
매체·유형 메타(문서 상단 목적 기술, 카테고리 전략)에서의 언급은 대상 밖이다. 금지 지점은 **독자에게 읽히는 본문 프로즈**다.

Bad:
```markdown
면접에서 "이 용량은 어떻게 산정했나요?"라는 질문을 받았을 때 답할 수 있습니다.
한 각도에 매몰되지 않는 시야가 시니어로 가는 발판이라고 봅니다.
```

Good:
```markdown
"이 용량은 어떻게 산정했나요?"라는 질문에, 왜 스토리지가 경계인지까지 답할 수 있습니다.
한 각도에 매몰되지 않으려 여러 제약을 함께 놓고 판단했습니다.
```

블로그 등 평가자 지향 매체의 구체 어휘·예시는 `extensions/blog.md B9` 참조.

## T16. 개념 병렬에 `+` 기호 남용 금지

두 개념·방법론·구성요소를 `+` 기호로 병렬하지 않는다. 자연 연결어(`와`/`과`, `및`, 쉼표)로 풀어 쓴다.
`A + B`는 영어 기술 문서의 나열 습관이라 텔레그래프체로 읽히고, 저자가 둘의 관계(둘 다인지·결합인지·단계인지)를 명시하지 않은 채 기호로 뭉뚱그린 인상을 준다.

- 판단 기준: 그 자리에 `와`/`과`를 넣어 자연스러우면 `+`를 연결어로 바꾼다.
- 예외: 코드·명령·버전 문자열(`C++`, `Ctrl+C`)과 관용으로 굳은 기술 스택·구성 표기(`Certbot + Jenkins`, `JdbcTemplate + native SQL`)는 유지한다.

Bad:
```markdown
헥사고날 + DDD로 재편했습니다.
멀티모듈 + 서버 1대로 통합했습니다.
```

Good:
```markdown
헥사고날 아키텍처와 도메인 주도 설계(DDD)로 재편했습니다.
멀티모듈과 서버 1대로 통합했습니다.
```

## T17. 어휘를 문서 안에서 고정한다

같은 동작을 고유어와 한자어로 번갈아 쓰지 않는다. 한쪽으로 정하고 문서 전체에 유지한다.

**도메인 용어가 확립된 동작은 한자어를 유지한다.** 기술 문서에서 `측정`·`검증`·`배포` 는 행위를 지목하는 용어다. 범용 고유어로 내리면 격식은 낮아지지만 무엇을 한 것인지 흐려진다. `재다` 는 시간·길이·무게 어디에나 쓰이고 `측정하다` 는 계측을 지목한다.

| 자리 | 쓰는 말 | 예 |
|------|---------|-----|
| 도메인 동작 | 한자어 | `측정했다`, `검증했다`, `배포했다` |
| 명사·복합어 | 한자어 | `측정 대상`, `측정 절차`, `직접 측정` |
| 도메인 용어가 아닌 동작 | 고유어 | `썼다`, `나눴다`, `넣었다` |

Bad:
```markdown
## 어떻게 재볼까?

측정 조건을 밝힙니다. 세 구성을 같은 빌드에서 쟀습니다.
```

Good:
```markdown
## 어떻게 측정할까?

측정 조건을 밝힙니다. 세 구성을 같은 빌드에서 측정합니다.
```

**사람들이 쓰지 않는 한자어로 줄이지 않는다.** 위 표는 한자어를 쓸 자리를 정한 것이지 아무 한자어나 써도 된다는 뜻이 아니다. 판정은 그 말이 사전에 있는가가 아니라 **독자가 그 말을 쓰는가**다. 표준 용어로 등재된 말이어도 독자의 어휘에 없으면 풀어 쓴다. 한 단어로 줄일 수 있다는 것이 줄일 이유가 되지는 않는다.

**같은 어근이 반복돼 단조로워지면 동의어나 문장 구조로 끊는다.** 고유어로 내리는 것은 해법이 아니다. `측정` 이 다섯 줄에 한 번씩 나오면 `실측`·`계측`·`확인` 을 섞거나, 같은 문형이 회차마다 반복되는 구조 자체를 바꾼다.

**경량 동사를 제목에 올리지 않는다.** 판정 기준은 그 동사가 한 동작을 지목하는가다. `확인하다`·`진행하다`·`수행하다` 는 측정도 확인이고 코드를 보여주는 것도 확인이라 지목에 실패한다. 제목에는 실제 행위를 쓰고 본문에서는 허용한다.

## T18. 제목·요약은 담긴 내용을 지목한다

제목과 요약 소제목은 그 아래에 무엇이 있는지 가리킨다. 그 내용이 얼마나 중요한지 규정하지 않는다.

판정은 이렇게 한다. **그 수식을 지우면 제목이 가리키는 대상이 달라지는가.** 달라지지 않으면 수식이 정보를 담지 않은 것이므로 뺀다.

| 자리 | 쓰는 말 |
|------|---------|
| 결론을 앞에 두는 절 | `요약`, `결론`, `판정` |
| 대상을 밝히는 절 | 그 대상의 이름 |
| 무게를 붙이는 수식 | 쓰지 않는다 |

Bad:
```markdown
## 이 구조를 지배하는 세 가지
## 무엇보다 중요한 전제
## 설계의 본질
```

Good:
```markdown
## 요약
## 전제
## 설계 결정
```

두괄식은 **순서**의 문제다. 결론을 앞에 두는 것이고, 결론에 수식을 붙이는 것이 아니다. 두괄식으로 쓰라는 요구를 수사를 얹으라는 뜻으로 읽지 않는다.

본문에서 같은 수사가 격언 형태로 나오면 [T14](#t14-방어적변명조-프레이밍-금지) 가 다룬다. T18 은 제목·소제목 자리에 한정한다.

T11 은 `패턴`·`표준` 처럼 외부 공신력을 빌리는 어휘를 막고, T18 은 저자가 스스로 붙이는 무게를 막는다.

## T19. 수량과 순서는 숫자로 적는다

정보성 글에서 수량과 순서는 숫자로 표기한다. 숫자 표기가 정확하고 짧다. 읽을 때 한글로 읽는 것과 적을 때 숫자로 적는 것은 별개다.

| 대상 | Bad | Good |
|------|-----|------|
| 개수 | `두 곳`, `세 가지`, `한 건` | `2곳`, `3가지`, `1건` |
| 단위를 붙인 수량 | `하나의 트랜잭션` | `1개 트랜잭션` |
| 대명사처럼 쓴 수량 | `둘 다`, `셋뿐이라` | `2개 모두`, `3개뿐이라` |

**열거에 극적 표지를 붙이지 않는다.** `하나. / 둘. / 셋.`, `첫째/둘째/셋째` 는 순서를 말하는 것이 아니라 무게를 붙이는 장치다. 평범한 불릿으로 둔다.

Bad:
```markdown
**하나. 원본은 그대로 둔다.** ...
**둘. 쓰기 방식이 제약을 정한다.** ...
```

Good:
```markdown
- **원본은 그대로 둔다.** ...
- **쓰기 방식이 제약을 정한다.** ...
```

**개수를 숨긴 서술을 값으로 바꾼다.** `원인 중 하나` 는 전체가 몇 개인지 알려주지 않는다. 아는 값이면 `원인 4건 중 1건` 으로 적는다.

수량을 세지 않는 관용구(`한두 번`)는 대상이 아니다.

T7 은 `변화 0` 처럼 숫자를 형용사로 붙이는 것을 막고, T19 는 수량을 한글로 적는 것을 막는다. 방향이 반대라 충돌하지 않는다.
