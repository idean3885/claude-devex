# 아키텍처 익스텐션

> **Base**: `base/readability.md` + `base/tone.md` + `base/punctuation.md` + `base/ai-tells.md`
> **Adds**: 시점의 층 선택 + 층별 정지 조건 + 그림 자립 조건 + 그림 검증 + 그림 안 용어
> **Profile**: 적용 대상·base 대비 적용 강도·합격선은 [profiles.md](profiles.md) 가 정본이다.

아키텍처 문서에서 어긋나는 지점은 내용이 아니라 **시점** 이다. 무엇을 그릴지는 알아도 어느 높이에서 그릴지, 어디서 멈출지가 정해져 있지 않으면 매번 즉석에서 판단하고 두 방향으로 어긋난다. 한쪽은 그림 하나에 외부 의존과 내부 구조를 섞어 아무 질문에도 답하지 못한다. 다른 쪽은 클래스까지 내려가 코드가 바뀔 때마다 낡는다.

근거는 C4 모델(`c4model.com`, Simon Brown)이다. 표기법과 도구를 정하지 않고 **시점의 층만** 정하는 모델이라 기존 규칙과 겹치지 않는다.

---

## AR1. 시점을 먼저 고른다

그림을 그리기 전에 이 그림이 답하는 질문과 읽는 사람을 정한다. 층마다 둘이 다르다.

| 층 | 답하는 질문 | 읽는 사람 |
|----|-------------|-----------|
| 1 시스템 맥락 | 이 시스템은 누구와 무엇과 주고받는가 | 누구나. 개발자가 아닌 사람 포함 |
| 2 컨테이너 | 따로 배포되는 실행 단위가 무엇이고 어떻게 통신하는가 | 개발자·운영자 |
| 3 컴포넌트 | 한 컨테이너 안이 어떤 책임으로 나뉘는가 | 그 컨테이너를 고칠 사람 |
| 4 코드 | 그 책임이 어떤 구조로 구현됐는가 | 그 코드를 여는 사람 |

층을 섞은 그림은 만들지 않는다. 외부 시스템과 내부 클래스가 한 그림에 있으면 두 독자 중 누구도 읽지 못한다.

보조 시점 셋이 더 있다. 필요할 때만 쓴다.

| 보조 시점 | 쓰는 때 |
|-----------|---------|
| 시스템 조망 | 시스템이 여러 개고 그 사이 관계가 문제일 때 |
| 동적 | 순서가 구조보다 중요할 때 (요청 흐름·전이) |
| 배포 | 실행 단위가 어느 인프라에 놓이는지가 문제일 때 |

## AR2. 어디서 멈추는가

**과하지 않게** 의 기준이 이 항목이다. 층마다 그리는 조건이 다르다.

| 층 | 그리는가 | 근거 |
|----|----------|------|
| 1 | 그린다 | 외부 의존은 되돌리기 어렵다. 한 장이면 끝난다 |
| 2 | 그린다 | 배포 단위와 그 사이 통신은 문서 없이는 코드에서 읽히지 않는다 |
| 3 | 그 컨테이너를 고칠 사람이 있을 때만 | 읽을 사람이 없는 그림은 낡기만 한다 |
| 4 | 그리지 않는다 | 코드가 답한다. 필요하면 자동 생성한다 |

4층을 손으로 그리면 코드가 바뀔 때마다 그림이 거짓이 된다. 손으로 그린 4층 그림은 **문서가 아니라 부채** 다.

## AR3. 컨테이너는 배포 단위다

도커 컨테이너가 아니다. 따로 배포되고 따로 실행되는 단위다. 모바일 앱 하나, 서버 하나, 서버리스 함수 하나, 저장소 하나가 각각 컨테이너다.

이 오해가 남으면 2층이 인프라 구성도로 변한다. 그림에 이 한 줄을 적어 오해를 막는다.

## AR4. 그림이 스스로 설명한다

C4 는 표기법을 정하지 않는다. 그래서 도형·색·선이 무엇을 뜻하는지 **그 그림 안에서** 알 수 있어야 한다.

| 요소 | 조건 |
|------|------|
| 제목 | 몇 층인지 그림 안에 적는다 |
| 상자 | 이름 + 종류 + 한 줄 책임. 종류는 사람·시스템·컨테이너·저장소 중 하나 |
| 선 | 방향과 목적을 적는다. "연결" 같은 말은 아무 정보가 아니다 |
| 도형·색 | 종류를 나타낸다면 무엇이 무엇인지 알 수 있어야 한다 |

## AR5. 렌더해서 보고 넘긴다

그림은 렌더 결과가 산출물이다. 소스만 보고 넘기면 결함이 그대로 남는다. 실제로 나온 것들이다.

| 결함 | 소스에서 보이나 |
|------|-----------------|
| 선이 상자를 관통 | 보이지 않는다 |
| 라벨이 다른 라벨과 겹침 | 보이지 않는다 |
| 도형이 깨져 다른 종류로 보임 | 보이지 않는다 |
| 렌더러가 태그를 지워 라벨이 한 줄로 붙음 | 보이지 않는다 |

렌더 확인이 한 번의 눈검사로 끝나지 않게 명령으로 남긴다. 고칠 때마다 다시 봐야 한다.

## AR6. 선은 직각으로

수평·수직으로 잇는다. 대각선은 상자를 스치고 라벨과 겹친다. 어느 상자에서 나왔는지도 흐려진다.

꺾을 자리는 상자 밖으로 잡는다. 여러 선이 한 통로를 지나면 그 통로를 하나로 모아 교차를 한 곳에만 둔다.

## AR7. 그림 안 용어도 독자의 말로

문서 본문에서 고친 조어가 그림에는 남는다. 그림은 따로 고쳐야 하므로 검증에서 빠지기 쉽다.

`base/tone.md` T17(어휘 층위 고정)과 같은 기준을 그림 라벨에도 적용한다. 문서와 그림에서 같은 것을 다르게 부르면 독자가 둘을 다른 것으로 읽는다.

## AR8. 그림이 못 답하는 것은 글로

그림은 무엇이 있고 무엇과 이어지는지를 보여주지만 **왜 그렇게 했는지** 는 보여주지 못한다. 근거는 글로 적는다.

| 담는 것 | 자리 |
|---------|------|
| 무엇이 있고 무엇과 이어지는가 | 그림 |
| 왜 그 구조인가, 무엇을 기각했는가 | 본문 |
| 되돌리기 어려운 결정과 그 대가 | 결정 기록 |

## 필수 구조

| 절 | 담는 것 |
|----|---------|
| 전제 | 이 설계가 성립하는 조건. 무엇이 정해져 있고 무엇이 열려 있는가 |
| 시점별 그림 | 1층과 2층. 3층은 조건에 맞을 때만 |
| 결정과 근거 | 쓴 패턴마다 막는 문제 · 대안 · 기각 근거 |
| 하지 않은 선택 | 쓰지 않은 것과 그 이유. 없으면 검토된 적 없는 것과 구분되지 않는다 |
