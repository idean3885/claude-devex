# 외부 서비스 인증

에이전트가 외부 서비스 CLI 를 호출하다 인증 만료나 권한 부족을 만났을 때, 어떤 자격으로 진행할지 판단한다.

## 판단 기준은 수단이 아니라 속성이다

"브라우저 동의를 써라" 는 사람 없는 환경에서 즉시 깨진다. 수단을 지정하는 대신, 자격이 갖춘 속성으로 판단한다.

| 속성 | 왜 필요한가 |
|------|------------|
| 스코프가 발급 측에서 고정된다 | 클라이언트가 권한을 넓힐 수 없다 |
| 만료·회전이 있다 | 폐기 시점을 사람이 기억하지 않아도 된다 |
| 사람이 값을 손으로 옮기지 않는다 | 기기 이동·평문 기록·복사 경로가 사라진다 |

세 속성을 모두 갖춘 자격은 두 갈래다. 사람이 있는 환경의 브라우저 동의 기반 인증, 그리고 사람이 없는 환경의 신원 연동 단기 자격(CI 의 OIDC 연동 등).

정적 장기 토큰은 세 속성 중 둘이 없다. 금지 대상이 아니라 **보완이 필요한 선택**이다. 보완 조건은 아래 [정적 토큰을 쓸 때](#정적-토큰을-쓸-때)를 따른다.

### 기본값

세 속성을 갖춘 경로가 **그 권한에** 있으면 먼저 그것을 쓴다. 없으면 정적 토큰을 쓰고 보완 조건을 채운다.

"있는가" 는 서비스 단위가 아니라 **권한 단위**로 판단한다. 서비스가 브라우저 동의를 제공하더라도 그 권한이 스코프 목록에 없으면, 그 권한에는 없는 것이다. 재인증해도 열리지 않는다.

## 판단 순서

1. 인증 만료인지 권한 부족인지 구분한다
2. 필요한 권한을 특정한다 — 서비스 전체가 아니라 그 작업에 필요한 범위
3. 카탈로그에서 그 권한이 정식 인증 스코프에 있는지 확인한다
4. **있으면** — 정식 인증 명령을 사용자에게 제시한다. 어시스턴트가 대신 실행하지 않는다. 브라우저 동의는 사람만 할 수 있다
5. **없으면** — 반복 여부로 갈린다
   - 한 번 하고 끝나는 작업: 사용자가 콘솔에서 처리하는 편이 빠르다
   - 반복되는 작업: 정적 토큰을 쓰고 보완 조건을 채운다
6. **사람이 없는 환경이면** — 신원 연동 단기 자격이 있는지 먼저 본다. 없으면 정적 토큰 + 보완 조건

브라우저 콜백이 필요한 명령은 세션 내 `!` 실행이 아니라 **사용자 본인 터미널**을 권한다. TTY 가 아니면 콜백이 걸린다.

## 카탈로그 (실측)

기억으로 판단하지 않는다. 확인한 사실만 적고 확인 시점을 남긴다. 스코프 목록은 서비스 쪽 사정으로 바뀌므로 이 표가 낡을 수 있다.

| 서비스 | 정식 인증 | 지원 그랜트 | 스코프에 없는 권한 |
|--------|-----------|-------------|--------------------|
| GitHub (`gh`) | `gh auth login` | Device Authorization, Authorization Code | — |
| Cloudflare (`wrangler`) | `wrangler login` | **Authorization Code + PKCE 만** | DNS 레코드 쓰기 — 27개 스코프에 `dns` 없음 (2026-08 확인) |

### 그랜트 타입은 클라이언트가 고르지 않는다

어떤 흐름을 쓸 수 있는지는 **인증 서버가 무엇을 구현했는지**로 결정된다. CLI 쪽에서 선택하는 항목이 아니다.

| 흐름 | 사람이 하는 일 | 전제 |
|------|----------------|------|
| Authorization Code + PKCE (loopback) | 같은 기기 브라우저에서 승인 | 브라우저가 같은 기기에 있어야 한다 |
| Device Authorization | 다른 기기에서 주소 열고 승인. CLI 는 폴링 | 브라우저 없는 기기에서도 된다 |

Device Authorization 의 존재 이유는 보관을 없애는 것이 아니라 **브라우저와 토큰 받는 쪽이 같은 기기가 아니어도 되게 하는 것**이다. SSH·CI·헤드리스가 대상이다.

지원하지 않는 서비스가 있다. Cloudflare 는 문서에서 Device Authorization 을 명시적으로 배제한다.

### 자기 서비스에 OAuth 를 붙이는 경우는 반대편이다

자기 API 에 인증을 구현하는 쪽이라면 그랜트 선택권이 있다. 헤드리스 소비자를 지원해야 하면 Device Authorization 을 구현할 수 있다.

이 문서는 **남의 인증 서버를 쓰는 소비자** 입장을 다룬다. 두 상황을 같은 문제로 보면 안 된다.

## 정적 토큰을 쓸 때

되돌릴 수 있게 만드는 것이 조건이다. 아래를 채운다. 채울 수 없는 항목이 있으면 그 항목을 조용히 넘기지 않고 사용자에게 알린다.

- **스코프**: 그 작업에 필요한 권한만. 리소스 범위도 좁힌다 — 계정 전체가 아니라 대상 하나
- **만료**: TTL 을 건다. 발급처가 지원하지 않으면 폐기 예정일을 기록한다
- **폐기 경로**: 콘솔에서 지울 수 있는지 미리 확인한다
- **보관**: OS 보안 저장소. 평문 파일·레포·로그에 남기지 않는다
- **입력**: 값은 사용자가 본인 터미널에서 넣게 한다. 대화에 붙여넣지 않도록 안내한다

```bash
read -rs TOKEN && <저장 명령> && unset TOKEN
```

OS 보안 저장소는 평문 파일을 없애는 장치이고, **같은 로그인 세션에서 실행되는 코드로부터는 보호하지 않는다.** 그래서 대응은 접근 통제가 아니라 권한 최소화와 주기적 폐기다.

### 정식 인증의 이득을 과장하지 않는다

정식 인증도 갱신 토큰을 디스크에 둔다. 평문 파일에 두는 CLI 도 있다. 이득은 "보관이 사라진다" 가 아니라 **스코프가 발급 측에 고정되고, 회전이 돌고, 사람이 값을 만지지 않는다**는 것이다. 보관 위치는 서비스 구현에 달렸고, 그 사실을 숨기지 않고 알린다.

## 강도는 소비자가 정한다

이 문서는 판단 재료와 기본값까지만 정한다. 얼마나 엄격하게 갈지는 레포·조직·개인이 선언한다. 같은 기준에서도 무인 실행 비중이나 감사 요구에 따라 답이 갈리므로, 강도를 이 문서에 고정하지 않는다.

선언 예시 — 소비자 측 지침에 둔다.

```markdown
## 외부 서비스 인증

정적 장기 토큰을 기본값으로 두지 않는다. 세 속성(스코프 고정·만료·사람이 값을 만지지 않음)을
갖춘 경로가 그 권한에 있으면 그것을 쓴다. 없으면 스코프·TTL·폐기 경로를 채워 정적 토큰을 쓴다.
```

강도를 올릴 때는 **검증 장치를 함께 둔다.** 규범을 문장으로만 두면 준수 여부가 독해에 좌우되고, 마찰이 실무 한계를 넘으면 규범 밖에서 우회본이 생긴다. 우회본은 관리 대상에 들어오지 않으므로 규범이 없는 상태보다 나쁘다. 발급한 자격에 만료가 있는지 점검하는 스크립트 한 개가 규범 세 줄보다 실효가 크다.
